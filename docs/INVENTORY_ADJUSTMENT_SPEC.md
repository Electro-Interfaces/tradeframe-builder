Связанные документы: `FUEL_ACCOUNTING_SYSTEM.md`, `API_SHIFT_REPORTS.md`, `TANK_CALIBRATION.md`

## 1. Контекст

В TradeFrame ведётся учёт остатков топлива в резервуарах АЗС (см. модуль «Остатки», `src/pages/FuelInventory/`). Источник данных — STS API (`/v1/tanks`, `/v1/report/shift_report`), движение топлива формируется по сменным отчётам.

Периодически на АЗС выезжает **комиссия для физической инвентаризации** — производятся реальные замеры остатков топлива в резервуарах. По результатам комиссия может зафиксировать **расхождение** между книжным остатком (расчётным по системе) и фактическим — в большую или меньшую сторону.

Расхождение оформляется **приказом генерального директора компании** (юридический документ). Только после утверждения приказа корректировка может быть внесена в учёт.

## 2. Текущая процедура (без TradeFrame)

1. На текущей смене АЗС закрывается сменный отчёт.
2. Комиссия выезжает на станцию и проводит замеры.
3. Открывается следующий сменный отчёт. **В нём корректировки ещё не применены** — он работает на «как было».
4. Комиссия возвращается, оформляет акт инвентаризации, акт идёт на утверждение генеральному директору.
5. После утверждения формируется приказ с конкретными значениями корректировок по каждому резервуару станции.

После этого начинается развилка по типу станции:

### Кейс 1 — АЗС с операторами (уже работает)

Приказ с корректировками передаётся на АЗС. Перед открытием очередной смены оператор вводит корректировки вручную через интерфейс терминала на станции. Корректировки попадают в открывающуюся смену через нативный механизм STS/poscontrol.

Этот кейс **не требует доработок** в TradeFrame.

### Кейс 2 — Автоматизированные АЗС без операторов (АКАЗС)

На АКАЗС нет физического оператора, который мог бы ввести корректировку перед открытием смены. Сейчас этот процесс заблокирован — приказ есть, а внести его в систему некому.

**Этот кейс реализуется в данном ТЗ.**

## 3. Что делаем

В TradeFrame добавляется функциональность:

1. Уполномоченный пользователь заполняет в TradeFrame **электронную форму корректировки** для конкретной АКАЗС (или группы) — на основании приказа генерального директора.
2. Форма сохраняется как документ с автором, датой, реквизитами приказа.
3. **Перед открытием следующей смены** на станции (или в момент формирования сменного отчёта в TradeFrame) система **автоматически применяет** введённые корректировки к остаткам резервуаров.
4. Применение фиксируется в журнале аудита и видно как отдельная позиция в сменном отчёте — для прозрачности.

## 4. Функциональные требования

### 4.1 Документ корректировки

Сущность «Корректировка остатков по инвентаризации» содержит:

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `id` | UUID | да | Внутренний идентификатор документа |
| `network_id` | UUID | да | Сеть АЗС (FK `networks`) |
| `trading_point_id` | TEXT | да | Конкретная станция (FK `trading_points`) |
| `order_number` | TEXT | да | Номер приказа генерального директора |
| `order_date` | DATE | да | Дата приказа |
| `inventory_date` | DATE | да | Дата фактической инвентаризации (когда комиссия выезжала) |
| `effective_at` | TIMESTAMPTZ | да | С какого момента применяется (см. §4.3) |
| `commission_members` | TEXT | нет | ФИО членов комиссии, проводившей замер |
| `comment` | TEXT | нет | Комментарий, причина расхождения |
| `attachment_url` | TEXT | нет | Скан приказа (см. открытый вопрос §11) |
| `status` | ENUM | да | `draft` / `scheduled` / `applied` / `cancelled` |
| `created_by` | UUID | да | Автор документа в TradeFrame |
| `applied_at` | TIMESTAMPTZ | нет | Когда фактически применилась корректировка (заполняется системой) |
| `created_at` / `updated_at` | TIMESTAMPTZ | да | Стандартный аудит |

Дочерняя сущность «Корректировка по резервуару» (1:N к документу):

| Поле | Тип | Обязательно | Описание |
| --- | --- | --- | --- |
| `adjustment_id` | UUID | да | FK на документ корректировки |
| `tank_number` | INT | да | Номер резервуара на станции (как в `/v1/tanks`) |
| `fuel_code` | INT | да | Код топлива (как в STS — `service_code`) |
| `book_volume` | NUMERIC | да | Книжный (расчётный) остаток на момент инвентаризации, литры |
| `actual_volume` | NUMERIC | да | Фактический замеренный остаток, литры |
| `delta_volume` | NUMERIC | да | Корректировка = `actual_volume − book_volume` (может быть отрицательной) |
| `book_mass` | NUMERIC | нет | Книжная масса, кг (если применимо) |
| `actual_mass` | NUMERIC | нет | Фактическая масса, кг |
| `delta_mass` | NUMERIC | нет | Корректировка по массе |

### 4.2 Жизненный цикл документа

```
draft → scheduled → applied
              ↓
          cancelled (до applied)
```

- **draft** — пользователь начал заполнять, но не отправил на применение.
- **scheduled** — документ утверждён в TradeFrame, ждёт момента применения (на следующей смене после `effective_at`).
- **applied** — система применила корректировку к сменному отчёту. Из этого статуса документ нельзя отменить (только сторнировать новым документом).
- **cancelled** — документ отменён до применения. Применяться не будет.

### 4.3 Правила применения и ограничения по времени

1. **Корректировка применяется только к смене, открытой после `effective_at`.** Если на момент `effective_at` смена уже открыта, корректировка применится к **следующей** смене.
2. Минимальный лид-тайм: документ должен быть переведён в `scheduled` **не позднее, чем за N минут до `effective_at`** (значение N — параметр конфигурации, по умолчанию 30 минут — см. открытый вопрос §11).
3. Если лид-тайм нарушен — система не блокирует сохранение, но автоматически сдвигает `effective_at` вперёд на N минут и помечает поле «фактическое время применения отличается от запрошенного».
4. Корректировка применяется **один раз** — после применения статус `applied`, повторно не сработает.
5. На одну станцию может быть **несколько активных** документов в статусе `scheduled` с разными `effective_at` — система обработает их в хронологическом порядке.

### 4.4 RBAC

- **Создание/редактирование документа в `draft`** — пользователь со scope `network` или `trading_point`, имеющий разрешение `inventory.write` (новое право).
- **Перевод в `scheduled` (утверждение)** — пользователь с разрешением `inventory.approve` (новое право; обычно — администратор сети или старший бухгалтер).
- **Отмена документа в `scheduled`** — тот же `inventory.approve`.
- **Просмотр всех документов** — пользователь с разрешением `inventory.read`.
- **Применение** — выполняется системой автоматически, без участия пользователя.

### 4.5 Аудит

Каждое изменение статуса документа и каждое его применение фиксируется в `audit_log` (существующая таблица, см. `server/routes/audit.js`). Запись содержит: автора, время, старое/новое значение, ссылку на документ.

## 5. UX

### 5.1 Где разместить

Новый раздел **«Инвентаризации»** в навигации:
- Уровень сети — список всех документов корректировки сети (`/network/inventory-adjustments`).
- Уровень торговой точки — документы только этой точки (`/point/inventory-adjustments`).

Также в существующем разделе «Остатки» (`/network/fuel-inventory`) добавить колонку «Последняя инвентаризация» с датой и ссылкой на документ.

### 5.2 Список документов

Таблица: дата приказа · станция · номер приказа · `effective_at` · автор · статус · сумма дельт по объёму (Σ `delta_volume`).

Фильтры: статус, сеть, станция, период (по `inventory_date` или `effective_at`).

### 5.3 Форма документа

Пошаговая форма:

1. **Шапка**: сеть, станция, номер приказа, дата приказа, дата инвентаризации, `effective_at`.
2. **Резервуары**: автоподтягивание текущих резервуаров станции из `/v1/tanks`. По каждому резервуару:
   - Тип топлива (берётся из STS, не редактируемый)
   - Поле «Книжный остаток» (предзаполнение из STS, не редактируемый — фиксируется на момент создания)
   - Поле «Фактический остаток» (вводит пользователь)
   - Автоподсчёт `delta_volume` с подсветкой знака
3. **Дополнительно**: комиссия, комментарий, прикрепить скан приказа.
4. **Кнопки**: «Сохранить как черновик» / «Утвердить (запланировать применение)».

При утверждении — диалог подтверждения с напоминанием о лид-тайме.

### 5.4 Просмотр применённой корректировки

В сменном отчёте (страница `ShiftReportsV2`, `/point/shift-reports`) первой смены, в которой применена корректировка, отображать **блок «Корректировка по приказу»** — со ссылкой на документ инвентаризации, и каждой записью корректировки на отдельной строке. Это нужно, чтобы итоговые цифры сменного отчёта были прозрачны для бухгалтерии.

## 7. Интеграция с механизмом сменных отчётов

Это самая сложная часть, и она **требует проектного решения** до старта реализации. Ниже три варианта, которые надо обсудить:

### Вариант A — корректировка как «фантомный слой» в TradeFrame

TradeFrame продолжает читать сменные отчёты из STS как есть. Перед отдачей на UI/Excel-экспорт **накладывает** на данные смены корректировки из своих документов в статусе `scheduled` с `effective_at <= shift.dt_open`.

Плюсы: ничего не пишем в STS, все остатки в TradeFrame корректны.
Минусы: STS-данные на стороне poscontrol остаются «как было», и любой отчёт прямо из poscontrol будет показывать старые остатки.

### Вариант B — пуш корректировки в STS API

При наступлении `effective_at` backend TradeFrame через STS API передаёт корректировку в poscontrol, и она попадает в открывающуюся смену нативно.

Плюсы: данные в poscontrol корректны, TradeFrame ничего не накладывает поверх.
Минусы: **не известно, есть ли в STS API такой эндпоинт.** Требуется уточнение у Гаврилова.

### Вариант C — гибрид

При наличии STS-эндпоинта — пушим в STS (вариант B). Если нет — fallback на фантомный слой (вариант A).

**До решения по варианту бэкенд-часть не проектируется.** См. §11, открытый вопрос 1.

## 8. Edge cases

| Кейс | Поведение |
| --- | --- |
| Документ создан, но `effective_at` уже прошёл, и смена за это время открылась | При утверждении (`schedule`) сдвинуть `effective_at` к моменту открытия следующей смены, предупредить пользователя |
| Станция в офлайне в момент `effective_at` | Применение откладывается до следующего сменного отчёта; статус остаётся `scheduled` |
| Несколько `scheduled` документов на одну станцию с одинаковым `effective_at` | Запретить на уровне БД (UNIQUE по `(trading_point_id, effective_at, status='scheduled')`); пользователь должен выбрать один |
| Резервуар перестал существовать (декомиссионирован) между датой инвентаризации и `effective_at` | Эта строка корректировки игнорируется при применении, в журнале — предупреждение |
| Тип топлива в резервуаре изменился между датой замера и применением | Документ блокируется в `applied`, оператор должен создать новый |
| Сеть/станция выбрана через alias (см. `network_trading_point_aliases`) | Документ привязывается к **физической** `trading_point_id`, а не к alias-сети. Корректировка применяется к реальной смене конкретной АЗС |

## 9. Безопасность данных

- Корректировка может уменьшить или увеличить остаток на сотни тысяч литров — финансовые последствия большие. На уровне UI — обязательное второе подтверждение при утверждении.
- В журнале аудита фиксируется не только статус, но и **снимок значений** (book/actual/delta) на момент изменения — чтобы при изменении `actual_volume` после первичного утверждения была история.
- Формат прикреплённого скана приказа — PDF/JPG, размер не более 10 МБ, проверка MIME (см. `src/utils/sanitize.ts`).

## 11. Открытые вопросы (требуется решение до старта)

1. **Интеграция с STS** (см. §7) — какой вариант (A/B/C) выбираем? Уточнить у Гаврилова, есть ли в `/tms` API возможность зарегистрировать корректировку остатка резервуара между сменами.
2. **Минимальный лид-тайм** (`N`) — 30 минут разумно? Уточнить у бизнеса.
3. **Кто имеет право утверждать** (`inventory.approve`) — главный бухгалтер сети, директор сети, генеральный директор холдинга? От ответа зависит конфигурация роли.
4. **Прикрепление скана приказа** — обязательно или опционально? Где хранить файлы (FS на сервере, MinIO, S3)?
5. **Что делать с уже произошедшими инвентаризациями** (исторические данные за прошлые периоды) — заводить ли их задним числом, или новый процесс работает только «вперёд»?
6. **Уведомления** — нужно ли отправлять Telegram-уведомление автору и согласующему при изменении статуса документа?
7. **Excel-экспорт** — должен ли документ корректировки экспортироваться отдельно в формате, удобном для бухгалтерии?
8. **Multi-сеть холдинга** — приказ по нескольким станциям сразу: один документ на N станций, или N отдельных документов?
